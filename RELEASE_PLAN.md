The launch price is fixed for now. Use store-generated local prices, keep the GitHub APKs available, and defer decisions about future pricing and early buyers. Automatic local prices reflect currency conversion, taxes, and pricing conventions; they do not guarantee equivalent affordability across income levels. See [Apple pricing](https://developer.apple.com/help/app-store-connect/manage-app-pricing/set-a-price) and [Google pricing](https://support.google.com/googleplay/android-developer/answer/6334373?hl=en).

Before the first paid release, complete the following work:

- **Keep the current storage.** AsyncStorage is sufficient for this scope. SQLite is optional and does not provide synchronization by itself. Development data can be reset before launch; once customers use the app, updates must preserve their saved data.
- **Add activity CSV import.** Export stable event IDs, exact timestamps, explicit nap state, notes, custom activity names, and estimate provenance. Import missing IDs and skip IDs already present, preserving newer edits. Validate the complete file before saving and show the import result. Support Puptime's own CSV format, including quoted commas, quotes, multiline notes, and Unicode. Routine and preference recovery are outside this activity import.
- **Preserve estimates as estimates.** Unaccepted missing-log suggestions stay outside saved history and CSV. Saved estimated entries retain an Estimated marker in storage, history, Timeline, export, and import. Count estimates separately from recorded entries and exclude them from routine learning and further missing-log detection.
- **Harden local saving.** Recover the write queue after a failed save, surface storage errors, and avoid treating unreadable saved data as an empty history that can then be overwritten. Verify app and widget logging, edits, naps, undo, and persistence across restarts.
- **Prepare the paid listings.** The metadata lane no longer overrides store pricing. Set the US base price to $1.99 and generate local prices in each store, then verify the result before publishing. Listing descriptions, review notes, and the privacy policy now cover activity recovery, persistent estimate labels, and both platforms' voice dictation. Final screenshots and live privacy disclosures still need review. Fastlane submission requires `APP_STORE_BUILD_NUMBER` for the verified uploaded build.
- **Verify store access.** Check active Apple membership, the paid-app agreement and payment setup, App Store Connect status, and Google account type and production eligibility. Local identifiers and release files do not establish live eligibility. Android submission configuration is still needed.
- **Run release verification.** Exercise CSV round trips and repeated imports, invalid-file handling, estimate provenance, existing unit checks, and native logging/widget flows on both platforms. Verify final signed release builds and listings before submission.

For the multiple-pet update, refine the Pet rows concept: show each pet's name and logging actions together on Log, and label every history entry with its pet. The online update follows these decisions:

| Area | Agreed behavior |
| --- | --- |
| Accounts | Local everyday use stays account-free. Owners sign in when enabling online features, using passwordless email codes matching Harpa's approach. |
| Roles | Owner and caretaker. Caretakers can add and correct activity logs, including the owner's entries, and start or end naps. Owners manage pets, routines, and access. |
| Links | One active caretaker link per pet. It remains valid until the owner stops sharing or replaces it. Revocation affects everyone using that link. Possession of a forwarded link grants access while it is valid. |
| IDs | Follow Harpa's readable three-letter prefix and random-string convention for new entities, such as pet_ and log_. A pet ID identifies a pet; a separate secret token grants caretaker access. |
| Web | A connected interface for quick logging, correcting logs, recent history, and viewing the routine. The first web scope is focused on caretaker tasks; owner administration remains in the phone app initially. |
| Local saves | Phone changes save immediately, including while offline. Keep pending changes durably and retry when the app is active and connected. Changes made while the app is closed can wait for its next activation. |
| Synchronization | Exchange individual log changes with stable IDs. Preserve independent additions and retry without duplicating them. For competing edits to the same log, the last server-accepted edit wins. Use deletion markers where needed so removed records do not return during synchronization. |
| Refresh | Retrieve updates on open or resume, after relevant writes, and through manual refresh. Live updates on an already-open screen are deferred. |
| Server | Start with a Cloudflare Worker for the API and web assets, Neon Postgres with Drizzle, and Better Auth. Reuse the relevant patterns from Harpa and Parrot rather than copying their unrelated infrastructure. Revisit SQLite only if it materially simplifies the durable sync implementation. |
| Idle work | No recurring empty cleanup jobs, background session polling, database health checks, or empty-queue discovery loops. Check access validity during requests and perform maintenance in response to actual work. |
| Attribution | Include actor and time metadata in the online design. Account-free link access identifies a session or supplied name, not a verified person. Full change history and rollback remain deferred. |

Account creation also requires the applicable account-deletion paths and privacy updates. Include these when adding accounts, alongside actual deletion of associated cloud data. [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/), [Google account deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).

Neon can suspend idle compute, but repeated queries can prevent it from staying idle. Audit authentication refreshes and monitoring as well as cleanup jobs. The operating requirement is zero unnecessary application-generated idle database queries. [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero).

Future pricing, early-buyer entitlements, full audit history, rollback, live synchronization, individual caretaker invitations, and broader web features remain deferred. Resolve those when their update is scheduled; they do not block the first release.

CSV recovery, estimate provenance, and persistence hardening are implemented. The app remains single-pet, local, and account-free. The current Log screen groups history by day and keeps three quick actions. Possible gaps appear as faded, unsaved Timeline marks; there is no explicit control to add a suggestion. Imported saved estimates retain their provenance and count separately from recorded entries. Current themed date/time controls and custom activity routine entries are retained alongside learned tolerance windows. Imports preserve existing edits, validate the whole file, and reject conflicting running naps. Widget completion preserves existing nap notes and estimate provenance. Storage still uses AsyncStorage; its write queue serializes one JavaScript runtime, not concurrent app and widget runtimes.
