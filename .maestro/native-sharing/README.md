# Native shared-care acceptance (not yet run)

These flows, `scripts/verify-native-sharing.mjs` and the source-tested
`scripts/native-sharing-adapters.mjs` are preparation for a separate test PR.
They are wired into the account runner's local `sharing-household` and
`sharing-temporary` scenarios, with no hosted workflow selection or native run.
No native pass, sharing feature fix, production-provider result or release
readiness follows from the small Node checks.

The thin runner adapter calls `verifyNativeSharing` for household or temporary
contributor, each with
its own fresh pair of synthetic accounts/devices. Reuse the existing installed
Better Auth SDK, local HTTPS Worker/D1/DO service, native host and evidence
helpers. Do not copy the account runner or introduce another service/client.

Preconditions are made by the real native UI/SDK: A has signed in, explicitly
enabled cloud and synced at least one pee log; B has signed in and has personal
logs but has not enabled personal cloud. Neither fixture has a walk log or an
existing invitation. Both use English and plain synthetic member names/labels.
This module never clears application state, inserts history, edits SecureStore
or seeds a cloud association. No genuine provider identity or owner record is
needed or allowed.

The adapter contract is:

- `activate(actor)`: stop/suspend the former actor before changing the current
  SDK/session/device binding. Two task-owned simulators retain separate real
  SecureStore identities; only one is active at a time. In particular, B must
  be stopped before transport goes online for A's revocation.
- `owner` and `carer` provide `flow(name, env, {secret})`, `snapshot({care})`,
  `cookie()`, `nativeShareCopy()` and `openURL(url)`. The carer's `accountId`
  comes from the actual native SDK account receipt. Its `attribution` is the
  independently observed member name, or the invitation label when the real
  account name is empty, never a hard-coded guessed actor ID.
- `flow` resolves the named new flows through the existing Maestro wrapper.
  `nativeShareCopy` only reads and clears the clipboard after the authored
  native Share/Copy step. `openURL` quietly opens the native scheme and handles
  any task-local system Open confirmation. Neither may print command arguments.
- `snapshot()` reads the personal database; `snapshot({care:true})` resolves
  the **actual accepted selection** and reads its separate care database. Both
  return the existing `{tables,events,owner,pending}` shape. Read all 14 tables
  in a single transaction, with no side-effectful application API.
- `readOwnerRecords({historyFor})` uses A's observed cookie against the real
  local service and returns `{records,revisions}`. Resolve requested local
  event IDs to their cloud IDs, paginate completely, and read history through
  the existing owner API. Never inject this cookie into B or the native SDK.
- `transport(mode)` reuses the existing controlled outage proxy and waits for
  prior forwarded requests to settle. `wire()` returns immutable cumulative
  `{pushes,accepted,pages,responses}` observer snapshots. Reuse its checked content-
  encoding decoder and zero-parse-error guard; do not change native bytes.
  `responses` contains only `{actor,shareId,forwarded,method,path,status}`:
  actor is the bound `owner`/`carer` context, shareId is the actual scoped share
  (or null for unscoped calls), and forwarded means an actual Worker response,
  never an outage generated by the proxy. Observe the shared header or accept
  request ID privately; retain no header/body/query/token/cookie. Both revoked
  scoped GET and stale POST accept must reach the service and return 410, the
  existing shared-authorization route contract. A later unscoped B account 200
  distinguishes revoked sharing from a dead account/session. Unchanged accepted
  counts alone never prove service authorization was exercised.
- `protectSecret(value)` registers tokens, copied/deep-link URLs and existing
  auth values for redaction before a command can fail. `fixtureOrigin` is the
  exact HTTPS loopback service origin, never a production host.

The new adapter implements transactional native snapshots using the installed
AsyncStorage selection, request-ticket session/account binding, service-derived
member labels, secret-safe sharing flows, clipboard/deep-link handoff, serial
actor binding and paginated owner inspection. Its Node checks use real SQLite
and synthetic service/driver inputs; no native case has executed.

The lifecycle runner supplies these injected hooks (no copied service or SDK):

- `bridge.activate({previous,device,email})` must terminate the previous app,
  settle forwarded requests, switch the owned simulator and bind the runner's
  device/email plus **inspector-only** cookie to that actor. It must not write
  SecureStore or insert an SDK session. Separate native credentials persist on
  the two simulators. Do not start any second native driver concurrently.
- `bridge.dataDirectory(device)` resolves that simulator's real app container.
  Snapshotting never creates or changes a DB. A care read requires both the
  actual persisted selection and an observed successful acceptance for the
  same SDK account/share. Missing or mismatched selection fails closed.
- `bridge.execute(binary,args,env)` and `bridge.simctl(args,input?)` capture
  quietly and never print raw arguments, output or thrown command objects.
  The sharing wrapper emits only finite phase failure names. `pbcopy` must
  pipe its supplied empty input so the invitation clipboard is actually cleared.
- The proxy calls `observer.begin({method,url,headers})` at request start,
  `observer.requestBody(ticket,decoded)` for creation/accept bodies, and
  `observer.finish(ticket,status,decoded)` **only for real Worker responses**.
  Do not call finish for proxy-generated offline errors. Initial SDK account
  or session responses bind each synthetic email/user to its actual cookie;
  later tickets capture that identity and the exact share/account headers,
  independently of the mutable active-device label. Request body tokens stay
  in memory and are immediately registered with the existing redactor.
- `readOwnerSharingRecords` receives a `get(path)` using A's observed cookie
  against the private local backend directly, bypassing the native observer.
  It paginates pull/history and reads A's sharing list into
  `observer.membership`, so the expected display actor is server-observed,
  never guessed from an ID. Retain only the scenario's finite aggregate result.

The CLI now creates A's and B's separate histories and signs each in through
the existing real UI/SDK helpers. Only A explicitly enables personal cloud;
B's journal stays local before accepting care. The proxy observes request-time
identity and scope, and private owner inspection bypasses it. Both scenarios
remain **unexecuted**. Existing native-host/artifact checks still apply; do not
remove a native-input rejection to run a later source on an older artifact.
An automated completion is `awaiting-attribution-visual-review`, never a final
native pass. No source check qualifies sharing, actor isolation or OS handoff.

Secret phases include invitation creation (its QR encodes the token), Share,
Copy, initial open/accept, revocation and stale-link acceptance. Discard every
driver output for these phases on success **and failure**, including global
Maestro startup logs, commands, screenshots, hierarchies and temporary flow
arguments. Keep the link only in memory and clear the clipboard immediately.
Do not pass it in Maestro environment variables or retain QR screenshots.
Only explicit post-accept history/attribution/access-ended images may be kept.
The future adapter must enforce this policy before any native execution.

Assertions cover exact prior activity and revisions, B's unchanged personal
14-table database, actual queued mutation/result acknowledgements, offline and
post-drain cold restarts, service revision actor plus owner-visible attribution,
and actual service-denied revoked work/stale invitations. Current source may
omit readable attribution from shared-sync writes; reproduce the red native
case before proposing a separate product change.

Attribution is two gates: the actual stored note/service actor, and **rendered
glyphs** in the owner UI. The Log row limits notes to two lines, so its complete
accessibility string cannot establish visible attribution after two newlines.
The flow captures that row and opens the existing full-note editor without
editing, captures its fully visible input, then closes it; all 14 SQL tables
must be identical across this inspection. A reviewer must open the detail
screenshot and see the expected actor legibly, without truncation, obscuring
keyboard or offscreen text. The module returns `awaiting-attribution-visual-review`,
never `ownerVisibleAttribution:true`; exit zero/AX matching is not the final
native pass. Record the reviewed image/source and result separately. If the
existing detail also clips attribution, report the red UI evidence.

Both strict stored and rendered attribution gates are attempted before a red
case stops. Only the explicit post-accept row/detail/access-ended images may
survive a failed non-secret phase; implicit failure screenshots, hierarchies
and raw driver logs are discarded. Every secret phase still discards all files
on success and failure. Opening detail must preserve all 14 tables even when
the attribution assertion fails.

`assertNativeDrained` remains strict and unchanged for the initial reproduction.
Before qualifying any future attribution fix that legitimately changes local
projection, freeze a case-specific expected transition from its concrete wire
receipts and projection boundaries, with all of these constraints:

- Only the one captured caregiver event's note may gain exactly
  `edited note + "\n\nLogged by " + independently observed actor`. Compare the
  returned record's complete data to that expected event; every other field,
  original event, pet, routine, setting and identity stays exact.
- Original outbox mutations stay byte-identical. Acks, mirrors and cursor come
  only from the exact accepted results and completed pulls, as today.
- Preserve the complete existing local-revision prefix. Construct the precise
  expected cloud revision chain for that event from the observed ordered pull
  boundaries, including exact before/after JSON, pet/local IDs, cloud source,
  next sequence and timestamps bounded by the measured projection window.
  Only those exact new rows and their corresponding sqlite sequence increment
  may differ; do not allow an arbitrary count of cloud revisions or copy the
  after-state revision list into expected values.
- Check any mandatory before-cloud-replace backup and its exact metadata/files
  independently. Do not suppress a backup/table difference to make drain pass.

Do not grant blanket events/history/metadata exceptions, mutate evidence, or
feed unchecked after-state tables into the existing strict helper. This exact
projection expectation is a prerequisite to green qualification of a future
fix, not implemented compatibility behavior or a present product change.

This does not cover genuine Google/Apple or email delivery, production web link
handoff, OS airplane mode, elapsed temporary-invitation expiry, Android parity,
or a release APK/AAB. A controlled outage and explicit revocation are the scope.
