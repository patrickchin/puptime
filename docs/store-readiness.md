[Apple definitions](https://developer.apple.com/app-store/app-privacy-details/), [Google form guidance](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en).

## Deletion acceptance and external resource

Apple requires account deletion within an account-creating app. The native flow and server cleanup are implemented, with separate qualification still required. The current Apple-revocation fallback and provider recovery-copy limits are described in [Apple deletion implementation](apple-account-deletion.md); verify deployment and actual retention rather than promising immediate erasure of every backup. [Apple guidance](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion).

Google separately requires a functional web resource naming Puptime/the developer, with a prominent way to request account and associated-data deletion **without requiring the app to be downloaded again**. An email intake or form can be suitable. An app-handoff page alone does not meet that description. [Google external-resource requirements](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).

### Implemented source and acceptance boundaries

`/delete-account` is a dedicated web utility linked from the website footer, app-handoff page and privacy policy. It verifies an **existing** account's email using the installed BetterAuth SDK, displays the verified account email, explains cloud versus device-local consequences, and requires an explicit checkbox and Delete action. It does not fetch puppy history, initialize optional analytics, store form values in browser storage, or continue deletion automatically after verification or a lost response. Cancel signs out the browser session and leaves cloud records intact.

The deletion-purpose header can only disable signup for the two existing OTP handlers. It is not authentication or deletion authority. The normal handler retains origin/CSRF checks, database-backed rate limits and hashed expiring codes. Ordinary native signup is unchanged. Before either OTP request the web client requires `/api/account/deletion-options` to explicitly advertise existing-account-only support and configured email; an older or misconfigured Worker fails closed instead of accidentally creating an account. The existing fresh-session and original-account fence authorize DELETE, using the same retirement path as native deletion. No schema, native/local storage or account-retirement behavior changes.

Local synthetic evidence must cover seeded email and provider-linked accounts using email OTP, unknown addresses (including a valid code from the ordinary signup route), expired codes/session, a changed browser account, cancellation, explicit deletion of populated synthetic cloud history, preserved throttling/origin refusal, absent rollout capability, and a lost accepted response without automatic retry/recreation. Seeded Google/Apple links are **not** genuine provider sign-in or delivered email. Browser screenshots and local tests do not establish a working hosted inbox or store acceptance.

## Encryption answers

`app.json` retains `ios.config.usesNonExemptEncryption=false`. In Expo this maps to Apple's `ITSAppUsesNonExemptEncryption=NO`: no encryption **or only exempt encryption**, including the linked libraries. It does not disable HTTPS/SecureStore or mean “unencrypted.” Expo documents this setting for SecureStore. [Apple key semantics](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption), [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/).

Apple distinguishes encryption limited to its operating system from non-OS algorithms; the former does not require documentation in App Store Connect. Puptime uses HTTPS and native secure credential storage. Inspect the final archive and all SDK crypto before affirming its exemption; source settings alone do not prove every linked SDK qualifies. The submit lane no longer automatically answers the broader legacy `export_compliance_uses_encryption=false` or `content_rights_contains_third_party_content=false` questions. It retains manual release and requires truthful completed console declarations rather than substituting a new guessed answer. [Apple documentation decision table](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption), [export questionnaire](https://developer.apple.com/help/app-store-connect/manage-app-information/determine-and-upload-app-encryption-documentation/).
