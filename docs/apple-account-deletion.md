# Apple authorization during account deletion

Account deletion remains an authenticated, recent-sign-in, explicitly confirmed action. The existing Better Auth `beforeDelete` hook first marks the owner `deleting`. Migration `0003-deleting-account-credentials.sql` then blocks credential inserts and updates for either the old or new deleting owner at the D1 statement boundary. This includes OAuth callbacks already exchanging a code; it does not block OTP recovery sessions or credential deletion.

Before removing credentials, the hook snapshots that owner's Apple accounts and attempts Apple's fixed HTTPS `/auth/revoke` endpoint, preferring each stored refresh token and otherwise using its access token. The current Services ID and client-secret JWT authenticate the request. A shared five-second abort signal bounds the upstream work, redirects fail closed, and token values/provider response bodies are never logged or returned. The current Better Auth configuration stores OAuth tokens without SDK encryption; this change does not change that setting.

HTTP 200 means `revoked`, including already-invalidated tokens. Missing tokens/configuration, timeout, network failure or another status produces `manual` while app-data deletion continues. No Apple account produces `not-linked`. The DELETE success response retains the SDK's cookie headers and adds `appleRevocation`. The website shows Apple Account instructions for `manual`; older or unknown outcome fields also receive conservative manual guidance without denying an acknowledged app deletion.

An app cleanup failure still fails deletion and retains identity credentials/session for a confirmed retry. The retiring owner remains fenced, and retrying upstream revocation is safe. This does not introduce a background deletion job or delete any retained qualification account.

Deploy migration 0003 before the server correction; the snapshot depends on its atomic write fence. Qualify with isolated Workers/D1 credentials and mocked Apple replies first. A later browser check must show the post-delete manual instruction/link and existing interrupted-deletion guard. Live Apple deletion requires a separately approved disposable account, not a retained sign-in fixture.

Live rows are removed on acknowledged deletion. Provider recovery copies expire separately: D1 Time Travel supports seven days on Workers Free or thirty days on Workers Paid; SQLite Durable Object recovery supports thirty days. The account object retains its non-content retirement tombstone. Operational database restoration must account for prior deletions rather than treating a historical backup as current consent.

Sources: [Apple account deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/), [TN3194](https://developer.apple.com/documentation/technotes/tn3194-handling-account-deletions-and-revoking-tokens-for-sign-in-with-apple), [Apple token revocation](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens), [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/), [Durable Object recovery](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).
