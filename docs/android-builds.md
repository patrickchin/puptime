# Android qualification artifacts

The existing **Android APK** workflow builds with local native Gradle through Expo prebuild. A manual run defaults to `publish=false`: it creates Actions artifacts and does not create a Git tag or GitHub release. Template QA builds reject `publish=true` before building; proposed upload-signed builds also require `publish=false`. Publication remains held until the exact candidate and intended delivery are qualified. Tag pushes keep their existing build-only behavior. The workflow-wide release lock covers both jobs.

Do not dispatch a candidate build until its source is frozen and the run is authorized. This workflow change alone produces no APK/AAB and establishes no runtime or store acceptance. It does not use paid EAS services, create or enroll a keystore, configure signing secrets, or change installed app data.

## Outputs

- `puptime-android-apk`: the existing `app-release.apk` contract, retained for the separate manual publisher and other consumers.
- `puptime-android-aab`: `app-release.aab`, built by the same Gradle invocation for qualification, not uploaded to Play or attached to the GitHub release.
- `puptime-android-qualification`: both file digests, signature/certificate receipts, the decoded **packaged APK** manifest, the AAB's actual raw protobuf manifest, and source/run/configured-version metadata. `BUILD-INFO.json` labels configuration values; inspect the packaged manifest rather than treating those values as measured artifact fields.

Signature/archive checks and the existing known-restricted-audio guard must pass before artifacts are uploaded. The publish job downloads only this run's APK and checks it against the verified build's digest before producing the unchanged `Puptime-<version>.apk` and APK-only `SHA256SUMS.txt` release assets. It atomically creates a **new** tag at the checked-out source commit, refuses every existing tag (including annotated or same-source tags), then creates the release with `--verify-tag`. It never moves or overwrites a tag; `--target` alone would not validate an existing tag's source.

If release creation fails after tag creation, preserve the tag and verified artifacts. Stop and review the source/digest before using the separate explicitly authorized existing-tag publication path; do not delete/retarget the tag or rebuild silently. Retrying this fresh-tag path will refuse the existing tag.

The existing-tag publisher requires the reviewed source SHA, current run attempt, APK and qualification artifact IDs and whole-ZIP SHA-256 digests, and the APK's own SHA-256. It accepts only a successful artifact-only manual Android APK run from this repository. Before creating a release it checks the tag's resolved commit, current producer/job/artifact metadata and expiry, complete downloaded ZIP digests, build receipts, and the APK's measured package/version/versionCode and verified signer against those receipts. It repeats the metadata/tag checks immediately before publication and shares the release lock. These checks establish custody; they do not approve installation, production signing, runtime behavior, rights or store delivery. The separate publication authorization still applies.

## Disposable signing-transition evidence

The separate [disposable proof workflow](../.github/workflows/android-signing-proof.yml) consumes two already completed artifact-only runs. It pins the immutable app source separately from the reviewed driver source. Its full-tree guard permits only the two named tooling edits, the regular-file command-evidence helper and, for the explicitly selected experiment, the permission-evidence helper; every other path, blob and mode must match the app source. It does not build another app or adopt a production signing key.

The guest-only exercise targets one fresh offline API 36 x86_64 emulator and temporary QA signing material. A static signature/lineage pass, successful installation or launch command is not a history-preserving update pass. Acceptance requires the actual guest seed and widget binding, plain-key rejection, lineage bridge, later update and stage-specific preservation assertions. Rejected installs keep strict file-byte checks; final cold restart requires exact tables, UID/widget, logical SQLite schema/durable metadata and non-SQLite files. It does not cover nonempty SDK credentials, genuine providers, Play, OEM/ARM devices or API 24–32.

Read the bounded verification receipt's completed stages, actual failure and cleanup result. An unfinished stage is not a pass. Failure diagnostics retain only fixed command fields; at most one best-effort screenshot is permitted only for the exact fresh offline guest-setup or launcher-widget-binding failure. Missing or competing command states remain unknown. Raw driver output, databases, preferences, QA keys and APK copies are not uploadable evidence. Keep **Hold: no new APK** until the exact candidate's remaining gates pass.

The [November 16 offline API 36 x86_64 guest QA exercise](https://github.com/patrickchin/puptime/actions/runs/43822343466) passed the complete source-defined signing/update/cold sequence with verified owned cleanup. It used disposable QA keys and the explicitly selected lineage-capability experiment. Earlier failed attempts remain failed and their causes remain unknown. Actual production-key and distribution acceptance remain open; this is not a broader provider/device-matrix pass.

## Signing and final acceptance

The default `qa-template` mode retains the Expo template signer and creates qualification artifacts only. The explicit `beta-upload` mode requires a manual run at the exact reviewed main SHA, a non-template public certificate fingerprint, and `publish=false`. Before adding any credentials, configure the named `android-beta-signing` environment with main-only admission and required owner review. Keep credentials environment-scoped. The Gradle fragment reads a runner-private PKCS12 and environment values; build/configuration caches are disabled and private material is removed after the build. Both verified artifact certificates must match the expected public fingerprint before upload. These source checks do not establish that signing custody or Play enrollment has been configured.

Play App Signing uses a separate app-signing identity from the upload key. Qualify the actual track-delivered APKs/splits and certificate after upload; an upload-signed local APK is not interchangeable with Play delivery. A valid signature or a task named `Release` does not establish store readiness. Compare installed/GitHub, upload and Play certificates before any update recommendation. Existing installations may keep using their qualified version while fresh testers enter a separately qualified track; an owner update is not required merely to publish a tester build. Do not prescribe uninstall/clear-data to resolve a signer mismatch. Any future in-place signer transition needs its own data and credential-preservation proof.

The raw AAB manifest is preserved without adding a bundletool installer to the build. Decode/inspect it with official [bundletool](https://developer.android.com/tools/bundletool) during exact-AAB qualification. Inspect final package/version codes, production endpoints, permissions/background-media configuration, native library and 16 KB page compatibility, the current target-API policy, artifact rights, and Play track acceptance separately. AAB signing/upload-key verification and a data-preserving distribution transition remain gates. The owner's choice of iOS for shared account/history tests does not cover Android-specific configuration or signing.

See [store readiness](store-readiness.md) for the independent store gates and [Android command-line builds](https://developer.android.com/build/building-cmdline) for Gradle tasks. Typed manual inputs and job-level permissions follow [GitHub's workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).
